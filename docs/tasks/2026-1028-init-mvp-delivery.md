### Goal

1. Пользователь проходит настоящий сценарий двумя Instagram-аккаунтами: комментарий `pricing` → публичный ответ → вопрос об email в DM → ответ → ссылка в DM.
2. Сервис работает на существующем хостинге и домене; сценарий можно показать на демонстрации и повторить после перезапуска.

### Scope

1. [Plan](2026-1028-plan-start.md) хранит исходное задание, контекст и варианты решения. Здесь фиксируем, как его доставить. Общие правила: [FLOW.md](../../FLOW.md).
2. Рабочая основа MVP: один процесс, постоянное хранилище уровня SQLite, один подключённый аккаунт бренда и один настраиваемый сценарий. Второй аккаунт играет посетителя. Язык и способ запуска подтвердим по возможностям существующего хостинга; новый стек ради эксперимента не нужен.
3. Подключение аккаунта можно настроить вручную допустимым способом, без кабинета клиентов и универсального редактора. Сохраняем минимальную обработку повторов, ожиданий и ошибок. Многопользовательская платформа, дополнительные соцсети и масштабирование остаются вне первой поставки.
4. Текущий шаг: проверить доступ Meta и возможности хостинга, затем выбрать минимальный контракт и серверный стек. Роли ниже предложены для передачи существующим агентам; новый запуск агентов этим документом не заявляется.

| Шаг | Результат | Владелец | Зависимость / параллельность | Доказательство готовности |
|---|---|---|---|---|
| 0A. Живой доступ | Понятен допустимый путь подключения двух аккаунтов, получения комментария и отправки DM; названы конкретные недостающие доступы | research, GPT Astra + пользователь | Сразу; параллельно 0B | Проверенные требования и возможность выполнить пробный вызов; если нельзя - точный блокер |
| 0B. Хостинг | Известны способ запуска, адрес, HTTPS, постоянный диск и способ передачи конфигурации | worker-2 + пользователь | Сразу; параллельно 0A | Подтверждённые возможности существующего хостинга, без предположений о доступах |
| 1. Минимальная сборка | Выбраны серверный стек и простая БД; есть запускаемый HTTP-сервис и небольшой контракт между исполнением и Instagram | worker-1; ведущий фиксирует границу | После 0A/0B; краткий выбор | Один способ запуска, согласованные события и операции; зафиксированы области изменений |
| 2A. Исполнение | Искусственный комментарий проходит до вопроса и ожидания; ответ продолжает тот же запуск; состояние сохраняется | worker-1 | После 1; параллельно 2B | Воспроизводимый проход и продолжение после перезапуска |
| 2B. Instagram | Реальный комментарий становится внутренним событием; исходящие операции выполняются через официальный API | worker-2 | После 1; параллельно 2A | Реальные события и подтверждённые результаты API; секреты не входят в отчёт |
| 3. Облачный e2e | Собранный сервис работает на домене и обслуживает два аккаунта | worker-1 сводит приложение; worker-2 развёртывает; пользователь проверяет | После 2A/2B | Пользователь сам проходит полный сценарий, включая финальную ссылку |
| 4. Уборка и минимальная надёжность | Убрано лишнее; разобраны повтор события, перезапуск и отказ отправки | Каждый воркер в своей области | После первого живого e2e | Повторяемый сценарий, сохранённое ожидание, понятная ошибка; известные ограничения названы |
| 5. Демонстрация и сдача | Короткий README, запуск, ограничения, история работы и участие AI; готово живое демо | Ведущий + пользователь | После 4 | Демонстрация повторяется; README ссылается на настоящие коммиты и проверки |

5. Траектории и владение:

| Роль | Область | Передача результата |
|---|---|---|
| worker-1 | Сборка приложения, зависимости, исполнитель и хранение | В шаге 1 отдаёт worker-2 минимальный контракт и способ запуска; затем сводит адаптер и исполнитель |
| worker-2 | Адаптер Instagram, конфигурация развёртывания и хостинг | До шага 1 проверяет хостинг; код адаптера начинает после контракта. Не меняет общую сборку без передачи worker-1 |
| research, GPT Astra | Доступ Meta, контракт платформы, близкие реализации | Отдаёт проверенные ответы и ссылки в ответе. Ресерч аналогов не задерживает независимую реализацию; приоритет у блокеров живого пути |
| Ведущий | FLOW, init, общая траектория и задания агентам | Передаёт короткие задачи с нужными скиллами и способом проверки; сводит результаты и предлагает следующий шаг |
| Пользователь | Аккаунты, доступ к хостингу, продуктовые решения и живое демо | Предоставляет недостающие внешние входы безопасным способом и проверяет сценарий; писать код не требуется |

6. Первые входы от пользователя: два доступных Instagram-аккаунта и состояние подключения Meta; тип хостинга и домен. Секреты в таскфайл не записываем.
7. Маленькие локальные коммиты после законченных шагов: правила и план → запускаемый сервер → сохранённый разговор → реальный адаптер → облачный e2e → уборка → демонстрация. Реальные границы коммитов определяет сделанная работа, а не этот список.

### Decisions

1. Сначала дешёвый живой MVP, затем удаление лишнего и только потом оптимизация. Технические варианты из plan не являются обязательным списком компонентов.
2. Приоритет настоящей проверки выше полноты универсального дизайна. Блокер Meta выясняем до длительной реализации; искусственный режим не выдаём за e2e.
3. Зависимые задачи не выдаём за независимые: адаптер и исполнитель разрабатываются параллельно только после минимального контракта. До него worker-2 проверяет хостинг, research проверяет платформу.
4. Пользователь разрешил частые локальные коммиты и выбрал работу через агентов. История отражает настоящий процесс; описание использования AI оформляем в README после доставки.
5. Git работает локально; база для сравнения этой задачи не выбрана. Готовность облачной поставки подтверждается отдельной проверкой, а не наличием плана или коммита.
